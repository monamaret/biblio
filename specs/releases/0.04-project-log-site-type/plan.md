# Implementation Plan: v0.04 — Prove the platform on the technical project log

## Summary

Replicate the now-proven platform (CLI, content pipeline, theming, scaffold templates, MCP server, terminal view — all from v0.01–v0.03) onto a second, structurally different site type: a technical project log with a running, cross-cutting timeline of dated, tagged entries. Scaffold, author, and deploy a real project-log site; prove its distinctive behaviors — filtering by date/tag/project, and a repeatable daily "write an update" authoring rhythm — work end to end; and extend the v0.03 agent/terminal layer to this site type's own content shape and query surface. This release is explicitly a generalization test, not a redesign: any gap found is a defect to fix in the existing platform, never a sign it needs reshaping (spec Assumptions).

## Technical Context

**Language/Version**: Go 1.22+ (`biblio-cli` — no new commands; the existing `new --type=log` path is exercised, gaps fixed as defects) and TypeScript/React (project-log-specific scaffold template, filter UI, MCP tools, terminal rendering)

**Primary Dependencies**: The same confirmed stack as v0.01–v0.03 (Cobra/Viper/Bubble Tea CLI; React + Vite + React Router v7 + Wrangler site/Worker; `gray-matter`/`react-markdown`/`remark-gfm` content pipeline; in-Worker MCP server + `md4x` terminal rendering) — this release adds a project-log-shaped content schema, filter UI/query surface, and corresponding MCP tools/terminal renderings, not new infrastructure or libraries

**Storage**: Unchanged — a second `content-index.json` generated by the same indexing step now carries dated/tagged/project-attributed entries; filtering is computed over this same generated, in-memory-then-bundled JSON index (Principle V — no database escalation triggered by adding a second site type)

**Testing**: Go unit tests for the project-log content schema/slug derivation (extending `internal/content`), TypeScript/React tests for entry-list rendering and multi-dimension filtering (date range ∩ tag ∩ project — spec Edge Cases), MCP tool contract tests for the project-log-specific query surface, and an end-to-end "scaffold → author a run of dated entries → deploy → filter → agent/terminal query" integration check — written first per Principle VI; any platform gap this surfaces gets a failing test capturing the defect before the fix lands

**Target Platform**: A second, independently deployed instance of the same single-Worker topology proven in v0.02/v0.03 (Workers Static Assets + `/mcp*`, gated by `mcp_enabled`) — not a shared multi-site Worker (Principle V: each site is its own simplest-topology deployment)

**Project Type**: Web application replication — a second real site of a structurally different type, built from the same scaffold/CLI/pipeline/theming/MCP/terminal platform proven in v0.01–v0.03, plus the project-log-specific content schema and filter surface that platform must now prove it generalizes to

**Performance Goals**: Filtering returns only genuinely matching entries with no false positives or omissions, including combined multi-dimension filters (intersection semantics — spec Edge Cases, FR-003); a new day's entry appears after the normal build/deploy step with zero one-off structural adjustments (FR-004, Scenario 3)

**Constraints**: MUST use the same CLI surface already proven for the profile site type — no project-log-specific commands or flags beyond `--type=log` (FR-001); MUST NOT require special-case adjustments to scaffold structure or config to publish each new entry, once the authoring rhythm is established (FR-004); an MCP/terminal request whose shape only makes sense for the profile type (e.g. "get résumé") MUST be rejected clearly by the project-log site (spec Edge Cases, mirroring the v0.03 "unsupported capability" contract)

**Scale/Scope**: One real, live technical project-log site, proven across "several consecutive published entries" (SC-002) — independently demonstrable on its own evidence; documentation-site replication and the cross-type consistency check are deliberately deferred to v0.05 (spec Assumptions, SC-003)

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

- **Principle I (Single-Author, Minimal-Dependency Bias)**: PASS — no new dependencies, abstractions, or config knobs are introduced; this release proves the *existing* minimal surface (CLI, `mcp_enabled`, theme presets, content schema pattern) generalizes to a second content shape, exactly the kind of "escalate only on a documented real trigger" discipline Principle I requires. - **Principle II (One Pipeline, One Source of Truth)**: PASS — the project-log content schema, slug derivation, and filtering logic extend the same canonical Go-side `internal/content`/`index` packages (Principle II ownership), consumed unchanged by the TS/React filter UI and the MCP query layer; `tokens.css` for this site type is generated through the same single theming pipeline from v0.01/v0.06.
- **Principle III (CLI-First, Guided Experience)**: PASS — scaffolding, authoring, building, and deploying the project-log site use exactly the CLI surface already proven for the profile type (`new --type=log`, `index`, `dev`, `build`, `deploy`); FR-001 explicitly requires this. No new commands are introduced.
- **Principle IV (Text-First, Progressive Enhancement)**: PASS — the project-log MCP tools and terminal rendering extend the v0.03 text-first contract (clean Markdown/plain-text `content` first, any richer view strictly additive) to this site type's own structured-query and rendering surface (FR-005), per the same tier-i/ii terminal-view scope (no tier iii).
- **Principle V (Simplest Topology That Can Grow)**: PASS — a second site is a second independent single-Worker deployment of the same proven topology, not a shared multi-tenant Worker; filtering stays computed over the generated JSON index — introducing it is explicitly *not* the documented, real trigger Principle V requires before escalating to D1 or Vectorize.
- **Principle VI (Test-First Development, NON-NEGOTIABLE)**: GATE — every project-log-specific schema/filter/tool/rendering unit MUST have a failing test authored and reviewed first; any platform gap this generalization test surfaces MUST be captured as a failing test (the defect) before the platform fix lands — never fixed-then-tested.
- **Security & Operational Posture**: PASS — `mcp_enabled` remains the only MCP-related config surface for this site too; no new auth/access-control surface, exactly mirroring the v0.03 posture for a second site.

Any structural mismatch this surfaces is fixed in the shared platform code, not worked around with a parallel path.
