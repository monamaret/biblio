# Phase 0 Research: v0.01 — Scaffold and theme a site

**Input**: [plan.md](./plan.md) Technical Context — no `NEEDS CLARIFICATION` markers remained after drafting, because every open question this release would otherwise raise was already resolved in [`specs/research/001-static-site-platform-with-mcp.md`](../../research/001-static-site-platform-with-mcp.md) and [`specs/research/roadmap.md`](../../research/roadmap.md) §0.3 before this plan was written (per the constitution's Decision Recording & Research Workflow — research precedes planning, not the other way round). This document consolidates those prior decisions into the form this plan depends on, rather than re-litigating them.

## Decision: CLI command surface and syntax

- **Decision**: `biblio-cli new <project-name> --type=<profile|log|docs> --domain=<domain> --theme=<preset>`, with the Bubble Tea TUI driving an interactive prompt flow whenever flags are omitted; `biblio-cli dev` wraps `vite dev` + `wrangler dev` behind one command.
- **Rationale**: Confirmed in [roadmap §0.3](../../research/roadmap.md) — flags support quick repeat use/scripting, the guided interactive flow gives the one-time "create a site" moment the polish the Bubble Tea investment signals, and one `dev` command removes the friction of running two dev servers by hand for a single author with no team to coordinate across.
- **Alternatives considered**: Raw `package.json` scripts or hand-assembled CI steps for dev/build — rejected outright by Principle III (CLI-first, never a raw script as the primary surface).

## Decision: Distribution method

- **Decision**: GitHub Releases with prebuilt binaries via `goreleaser` as the primary path; `go install github.com/.../biblio-cli@latest` documented as the alternative for those with a Go toolchain.
- **Rationale**: Confirmed in [roadmap §0.3](../../research/roadmap.md) — a single private author needs at most two install paths; a package-manager tap (Homebrew, etc.) is distribution infrastructure for a multi-user audience `biblio` doesn't have (Principle I).
- **Alternatives considered**: Homebrew tap / multi-platform package managers — rejected as speculative multi-user infrastructure.

## Decision: Content-index shape and ownership

- **Decision**: `content-index.json` is generated by `biblio-cli` (Go side) as step 1 of the build pipeline, in a shape consumable both by React Router's `prerender` (v0.02) and the in-Worker MCP query layer (v0.03).
- **Rationale**: Principle II (One Pipeline, One Source of Truth) — designing the shape now to serve both later consumers avoids a second, divergent index format appearing when v0.02/v0.03 land.
- **Alternatives considered**: Per-consumer indexes (one for the site build, one for MCP) — rejected; would duplicate parsing/schema logic across Go and TS, the exact split Principle II forbids.

## Decision: Theming ownership and artifact

- **Decision**: `tokens.css` is generated once per site (by `biblio-cli`, from the chosen theme preset) and imported by both the site build and the future MCP App UI bundle (v0.03); one distinct preset per site type, selected at scaffold time.
- **Rationale**: Confirmed dependency noted directly in [`specs/releases/0.01-release.md`](../0.01-release.md) Assumptions — `tokens.css` generation (§1) depends on preset definitions (§6), so both are scoped into this one release rather than split, satisfying Principle II's "generated once, imported by both" rule from day one.
- **Alternatives considered**: Letting the site build generate its own tokens from a shared config — rejected; would create exactly the cross-language theming-logic duplication Principle II rules out.

## Decision: Local development workflow

- **Decision**: `biblio-cli dev` wraps `vite dev` + `wrangler dev` behind one command; no separate documented multi-terminal workflow.
- **Rationale**: Confirmed in [roadmap §0.3](../../research/roadmap.md) — matches the smooth, CLI-first DX the Bubble Tea investment already signals.
- **Alternatives considered**: Documenting a two-terminal manual workflow — rejected as friction inconsistent with Principle III.

## Decision: Storage and search posture for this release

- **Decision**: No database and no search capability ship in this release; the content index is a flat generated JSON file, and search itself doesn't exist until the MCP layer (v0.03) — which will start as keyword search.
- **Rationale**: Principle V (Simplest Topology That Can Grow) — escalate only on a documented, real trigger; this release introduces no trigger for either escalation.
- **Alternatives considered**: Pre-wiring D1 bindings or a Vectorize index "for later" — explicitly rejected; Principle I calls this exact kind of speculative scaffolding out by name.

## Open questions resolved

None remain — every Technical Context field was filled directly from confirmed decisions in `001-static-site-platform-with-mcp.md` and `roadmap.md` §0.3, with no `NEEDS CLARIFICATION` markers requiring a research task of their own.
