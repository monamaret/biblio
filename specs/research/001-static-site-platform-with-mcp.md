**Status:** In Progress

## Problem Statement

Design and build a private "platform" called `biblio` for creating static sites (built with React + Vite) where each finished, built site also exposes an MCP server on a `/mcp` endpoint, plus a `biblio-cli` tool that scaffolds new site projects and config.

- **Goal:** A reusable combination of React + Vite site templates/themes, paid-service integrations (Cloudflare Workers, GitHub, etc.), deployment guides, and a `biblio-cli` scaffolding tool that lets the owner stand up new sites — all on one domain/host — with a working `/mcp` endpoint backed by a custom-built MCP server.
- **In scope:** React + Vite site templates/themes; a custom-built MCP server (no third-party MCP hosting) served from the same domain/host as the site via Cloudflare Workers; deployment guides; the `biblio-cli` scaffolding tool; support for personal profile/CV sites, technical project logs, and project documentation sites.
- **Out of scope:** Productizing or selling to other users; supporting site generators/frameworks other than React + Vite unless it proves unsuitable.
- **Success criteria:** A working scaffold + CLI that produces a deployable React + Vite site with a functioning `/mcp` endpoint on the chosen hosting stack, validated by at least one real site.
- **Non-goals:** Building a general-purpose product for external users; multi-tenant SaaS concerns; supporting platforms outside the already-available stack; estimating timelines, developer hours, or other "real world" delivery metrics (see [roadmap.md](roadmap.md) for why).

## Background & Context

- **Relevant prior work:** [000-tech-stack.md](000-tech-stack.md) maps the paid platforms/services to `biblio` responsibilities — Cloudflare Workers and GitHub are the only load-bearing services (hosting/MCP/storage and source-control/CI respectively); OpenRouter is the preferred conditional candidate for build-time embedding generation if semantic search is ever escalated to (DeepSeek was ruled out — its API has no embeddings endpoint); GCP, Vercel, and Ragflow were evaluated and dropped.
- **Domain assumptions:** React + Vite is the site framework; the MCP server is custom-built and served from the **same domain/host** as the site (no CORS boundary), via a single in-Worker Cloudflare Worker; multiple independent sites will be built from this scaffold over time, so it must be repeatable. The two priority scaffolds are the **technical project log** (daily updates, high text volume) and **project documentation** — both need rich text formatting plus project- and tag-based filtering/sorting.
- **Stakeholders:** Project owner/admin — sole developer and primary user of `biblio-cli`.

## Architecture Patterns

`biblio` builds its own MCP server (no third-party MCP hosting). The site and `/mcp` endpoint must share **one domain and one host** as far as the visitor/client is concerned — no cross-origin boundary, no CORS to manage — which rules out an independently-hosted `mcp.<domain>` subdomain pointing at a separate origin.

- **Selected pattern:** **A single Cloudflare Worker serves both the static site (via Workers Static Assets) and the `/mcp` endpoint** — implemented directly in-Worker using the `agents`/`workers-mcp` SDK with Durable Objects for session state — **mounted on a route (`example.com/mcp`) rather than a subdomain**. This is the simplest possible topology: one project, one deploy, one origin, no proxying, no second backend, no new DNS — and the easiest shape for `biblio-cli` to scaffold and replicate consistently across many sites. Two GCP Cloud Run-based alternatives (a standalone Cloud Run service serving both site and MCP; a Worker front door proxying `/mcp*` to Cloud Run) were evaluated and dropped — see [architecture.md](architecture.md) for diagrams of the selected pattern and the alternatives considered. The route-vs-subdomain choice was decided on the same grounds: a route needs no extra DNS work and keeps scaffolding to one project/one deploy, and CORS — the original concern with subdomains — doesn't actually apply, since MCP clients connect directly as external HTTP/SSE clients rather than through the site's own browser JS.
- **Tradeoffs:** This commits the MCP server to the Workers runtime (V8 isolates, no containers) and to in-Worker/Durable-Object-based session state, in exchange for the simplest possible topology to scaffold and replicate across many sites.
- **Integration points:** React + Vite build output → Cloudflare Worker (served as static assets via the Workers Static Assets binding); custom MCP server → implemented directly in that same Worker using the `agents`/`workers-mcp` SDK, with Durable Objects for session state; `biblio-cli` → scaffolds the combined React + Vite + Worker project, `wrangler.jsonc`, route/custom-domain config, and MCP-related bindings — **gated behind a build-time configuration flag** so a site that doesn't want an MCP surface skips content-index generation, the route, and the bindings entirely. A single React + Vite + Tailwind + shadcn/ui stack spans the site itself and its MCP App UI, sharing one generated token file (`tokens.css`).
- **Build pipeline (three steps):** (1) **`biblio-cli` generates `content-index.json`** directly from the content directory — a Go-side generator (parsing frontmatter + body, mirroring what `gray-matter` would do in JS), run before the site build so both the site and the Worker can consume the same artifact; (2) **`react-router build`** (with `prerender` configured in `react-router.config.ts` to enumerate every content-driven route) prerenders every route to static HTML/CSS/JS, with the content index available to the `prerender` function and to content-driven pages (log-entry lists, docs TOC, etc.); (3) **Wrangler build/deploy** — the Worker `import`s `content-index.json` directly (inlined into the Worker's V8 bundle for in-memory querying, no extra fetch), and `wrangler.jsonc` binds the SSG output directory as static assets, with the Worker's fetch handler routing `/mcp*` to the MCP server and falling through to the assets binding for everything else. See [architecture.md](architecture.md) for a diagram of this pipeline and [deployment-guide.md](deployment-guide.md) for the end-to-end walkthrough.
- **Data model implications:** Since content is authored as Markdown + frontmatter and loaded at build time, the same content directory that builds the site also generates the MCP server's data — one source of truth, one pipeline, always in sync. This gives a natural **progressive-enhancement storage approach**:
  1. **Default — a generated JSON content index bundled into the Worker** (`content-index.json`, queried in-memory). For personal-scale content this is fast, requires **zero extra Cloudflare resources** (no D1 migrations, no KV namespace), and keeps `biblio-cli` scaffolding to "one more build step."
  2. **Escalate to D1 (SQLite)** only if a site's content volume or query needs (filtering, sorting, pagination across many fields) outgrow comfortable in-memory handling — still populated at build/deploy time from the same content directory, so it remains a derived artifact.
  3. **Escalate to Vectorize** only if semantic search becomes a real requirement — most plausible for the docs site type (e.g., an `explain_concept`-style tool) — generating embeddings at build time via OpenRouter (see [000-tech-stack.md](000-tech-stack.md)).
  - *Escalation thresholds (heuristic, not hard numbers — personal/portfolio scale):* JSON → D1 around the low-thousands-of-entries / megabyte range, or when genuinely relational queries are needed; keyword → Vectorize when conceptual/natural-language queries are poorly served by exact-keyword matching — a quality signal from real usage, most likely to surface first on the docs site type.

  **Tool surface per site type** (each maps directly onto the content-index shape):
  - *Personal profile/CV:* `get_profile`, `list_experience`, `list_skills`, `list_projects`, possibly `get_resume`
  - *Technical project log:* `list_entries` (filterable by date/tags/project), `get_entry` (by slug), `search_entries`
  - *Project documentation:* `get_toc`/`list_pages`, `get_page` (by slug/path), `search_docs` (keyword now, semantic later via Vectorize)
  - *Shared across all three:* `get_site_info` (site metadata), and a generic `search`

  **Frontmatter schema per site type** (what the build-time content-index generator parses and the tool surface above serves back):
  - *Personal profile/CV:* Profile (singleton) — `name`, `bio`, `links`; Experience — `title`/`org`/`location`/`start_date`/`end_date`/`summary`/`tags`; Skill — `name`/`category`/`level`; Project — `name`/`summary`/`url`/`tags`/`date`
  - *Technical project log:* Entry — `title`/`date`/`project`/`tags`/`summary`/`status` (`draft`/`published`); `slug` derived from filename
  - *Project documentation:* Page — `title`/`order`/`section`/`summary`; `slug`/`path` derived from file location, giving a natural nested tree
  - *Shared across all three:* a small site-level config (`site_name`/`description`/`site_type`) backing `get_site_info`

  **Per-site-type theming for MCP App UIs:** every theme defines the same shadcn/ui CSS-variable contract (colors + `-foreground` pairs, `border`/`input`/`ring`, `radius`, plus Tailwind font/spacing extensions). `biblio-cli` scaffolds distinct presets per type — *CV/profile:* warmer/personal palette, distinctive heading font, larger `radius`; *project log:* cooler/technical palette with monospace accents, tighter `radius`; *docs:* neutral/high-contrast palette tuned for long-form reading and syntax-highlighting legibility — each compiled into a single generated `tokens.css` imported by **both** the site build and the MCP App UI bundle, so the UI automatically inherits the site's exact look from one source of truth.
  - *Retro/terminal CSS research:* surveyed `terminal.css`, WebTUI, `system.css`, and `tui.css`. None will be adopted as a parallel framework — doing so risks class/utility collisions with Tailwind/shadcn and undermines the single-`tokens.css` design. Instead, **mine their palettes (Gruvbox/Catppuccin/Nord/Dracula — exactly the retro-terminal aesthetic wanted), monospace type choices, and box-drawing/CRT-style effects directly into the project-log and docs presets**. If a parallel framework is ever wanted after all, **WebTUI** is the strongest integration candidate — its CSS-layers + attribute-based syntax (`size-="large"`, `box-="square"`) is structurally the safest fit alongside Tailwind/shadcn, and its theme packages overlap directly with `terminal.css`'s palette families.

  **MCP App UI rendering — charts/visualizations and terminal-based hosts:**
  1. **No dedicated charting-library dependency.** Hand-roll minimal SVG/CSS chart components (timelines, skill levels, simple bar/line charts) styled directly with `tokens.css` — smallest footprint, zero new dependencies, automatically themed; consistent with `biblio`'s minimal-dependency bias (plain Markdown over MDX, bundled JSON over D1, framework-native prerendering over a separate SSG library).
  2. **Text-first, progressive-enhancement tool design.** Terminal-based MCP hosts generally cannot render HTML/React UI resources at all — they only see a tool's plain-text/Markdown `content`. Every tool that returns something chart-like must produce a clean, self-sufficient Markdown/ASCII rendering (a Markdown table, an ASCII bar/sparkline) as its primary `content`, with the rich SVG/HTML UI resource layered on top only for hosts that support it. The textual rendering is the baseline that must stand alone; the UI resource is a bonus, never a replacement.

  **Terminal/CLI-optimized view of the site:** researched as a complementary surface — not a replacement for the full site — that mirrors the text-first MCP rule above, applied to the site's own routes for `curl`/`lynx`/terminal-coding-agent clients that can't or won't run JS. Confirmed direction:
  - **Mechanism:** `Accept`-led content negotiation in the Worker's existing `fetch` handler (no new routes/DNS — same shape already preferred for `/mcp`), complemented by a `.md` URL-sibling convention and a minimal `llms.txt` for discoverability. **Layered detection** is the right approach: parse `Accept` q-values first (rank `text/markdown` vs. `text/html` by stated preference, don't substring-match); fall back to User-Agent matching only when `Accept` is uninformative (e.g., `Accept: */*`); use `sec-fetch-dest: document` — sent by every modern browser on top-level navigation — as a safeguard so a human never accidentally lands on raw Markdown; and set `Vary: Accept, User-Agent` on every negotiated response so Cloudflare's cache serves the correct variant. This is current, well-precedented 2026 practice — Cloudflare's own "Markdown for Agents" edge feature, Vercel's content-negotiation rewrites (99.37% size reduction reported), and the long-running `wttr.in`/`cheat.sh` family of User-Agent-branching console services all validate the approach; Bun reported a 10× token-usage reduction after switching to serving raw Markdown to Claude Code instead of rendered HTML.
  - **Rendering:** a spectrum from raw Markdown passthrough to a fully terminal-styled "mini-site" (reusing the retro/terminal token research above). **`md4x`** — a ~100 KB gzipped WASM Markdown renderer with a built-in `renderToAnsi()`, advertised as portable to "Deno, Bun, edge workers" — is the strongest candidate for rendering Markdown → ANSI directly in the Worker at request time, potentially collapsing the raw-passthrough and lightly-formatted tiers into "the Worker renders it on the fly," with no separate build-time pipeline needed.
  - A handful of narrowly-technical spikes remain before this can be built (confirming `md4x` runs in the Workers runtime, whether Cloudflare's "Markdown for Agents" reaches Worker responses, how far to invest in `llms.txt`, and whether a full terminal-styled mini-site is worth it) — tracked as tasks in [roadmap.md](roadmap.md).

## Security & Compliance

- **Threat surface:** Public `/mcp` endpoint exposed on custom domains; any data the custom MCP server stores or accesses; secrets/config handled by `biblio-cli` during scaffolding.
- **Data classification:** Likely low-sensitivity (personal CV/profile, project logs, docs) — confirm per site.
- **Compliance regimes:** None anticipated (private, non-commercial use).
- **Mitigations:** The `/mcp` endpoint is intentionally **public with no auth/access control** (low-sensitivity, read-oriented content and tools); standard Cloudflare protections (rate limiting, WAF, bot management) serve as the operational safety net rather than per-site auth. Still need a secrets-handling approach for generated config files.

Schemas: *Profile* — `name`/`bio`/`links`; *Experience* — `title`/`org`/`location`/`start_date`/`end_date`/`summary`/`tags`; *Skill* — `name`/`category`/`level`; *Project* — `name`/`summary`/`url`/`tags`/`date`; *Log entry* — `title`/`date`/`project`/`tags`/`summary`/`status` (slug from filename); *Docs page* — `title`/`order`/`section`/`summary` (slug/path from file location); plus a shared site-level config (`site_name`/`description`/`site_type`) backing `get_site_info`. Escalation thresholds are heuristic rather than hard numbers, given personal/portfolio scale: JSON → D1 when the bundled index grows into the low-thousands-of-entries / megabyte range or needs genuinely relational queries; keyword → Vectorize when search quality (not volume) shows conceptual queries aren't served well by exact-keyword matching, most likely first on the docs site type — Owner
- **2026-06-07** — The `/mcp` endpoint will be **public with no auth/access control**, and `biblio-cli` will provide a **build-time configuration option to opt in or out of generating the MCP content index and mounting the `/mcp` endpoint at all** — Owner's stated decision; resolves the open auth question. Given `biblio`'s low-sensitivity, read-oriented content and tool surface (`get_profile`, `list_entries`, `search_docs`, etc.), no per-site access control is needed — Cloudflare's standard protections (rate limiting, WAF, bot management) are sufficient operational safety nets. The build-time toggle preserves the in-Worker pattern's "simplest topology" for sites that don't want an MCP surface at all, letting `biblio-cli` conditionally scaffold the content-index generation step, route mounting, and bindings — Owner
- **2026-06-07** — Lock in the **on-disk content directory layout convention**: flat-by-concept directories under `content/`, not type-prefixed — `content/site.yaml` (shared site-level config), `content/profile.md` + `content/experience|skills|projects/*.md` (profile/CV sites only), `content/entries/YYYY-MM-DD-slug.md` (project-log sites only, slug = filename minus date prefix and extension), `content/docs/<section>/<page>.md` (docs sites only, nesting *is* the path/slug, `order` in frontmatter sorts within a section) — Owner confirmed this convention as proposed. Rationale: each `biblio` site has exactly one fixed `site_type`, so a `content/<site-type>/...` prefix (as sketched early in the roadmap) would add a redundant directory level `biblio-cli` already knows to skip; naming directories after the confirmed schema names (`experience/`, `entries/`, `docs/`, etc.) keeps the layout self-documenting for the one human author, gives `import.meta.glob` patterns and the Go-side content-index walker an obvious 1:1 mapping to site-type/content-type, and the `entries/`/`docs/` shapes directly satisfy the already-confirmed slug-derivation rules (filename for log entries, file location for docs pages) — Owner
- **2026-06-07** — Lock in the **build-time MCP opt-in/out configuration shape**: a single flat boolean, `mcp_enabled` (default `true`), alongside `site_name`/`description`/`site_type` in `content/site.yaml` — Owner confirmed this shape as proposed. Rationale: the research identified exactly one MCP-related, build-time configuration need (the toggle itself) — the public/no-auth decision already rules out per-site access-control config, and nothing else MCP-related has surfaced — so a nested `mcp: { enabled: ... }` object would be premature structure for a single value, against the project's minimal-dependency/no-speculative-abstraction bias; promoting to a nested object remains a trivial, backward-compatible migration if a second MCP-related setting is ever needed. Defaulting to `true` matches "every site gets `get_site_info` and a generic `search`" — opting out is the exception. At build time `biblio-cli` reads this single flag to decide, in one place, whether to generate `content-index.json`, mount the `/mcp*` route in the Worker's `fetch` handler, and include MCP-related bindings (Durable Objects, etc.) in `wrangler.jsonc` — Owner
- **2026-06-07** — Confirm the **Docs Page frontmatter schema needs no `tags`/`project` fields** (stays `title`/`order`/`section`/`summary`, unchanged), and `search_docs`/`get_toc` need no matching filter parameters — Owner confirmed. Rationale: `tags`/`project` exist on the project-log Entry schema specifically because that site type intentionally mixes entries **across multiple projects** into one chronological timeline, where cross-cutting filters are the only way to navigate it. A documentation site is structurally different — it's already scoped to the **one project** it documents, and its natural organizing principle is the confirmed hierarchical `section`/`order` structure (exactly what `get_toc`/nav generation is built on). "Configurable by site type" is already satisfied by the existing **per-site-type fixed-schema design** itself — each type's schema is independently tailored to that type's actual needs, which is why `tags`/`project` live only on the log Entry schema. Adding them to Docs (or a generic runtime-configurable schema/filter layer any type could opt into) would be schema surface and config-layer complexity built for a use case that hasn't surfaced — against the project's minimal-dependency/no-speculative-abstraction bias. If a docs-filtering need ever does arise, it gets its own research pass and Decision Log entry at that point — Owner
- **2026-06-07** — Adopt a **progressive-enhancement storage approach** for the MCP server's data, and confirm a per-site-type tool-surface sketch as the working direction — Owner confirmed this is the correct direction. Because content is authored as Markdown + frontmatter and loaded at build time, the same content directory can drive both the site build and the MCP server's data, keeping one source of truth and one pipeline. Concretely: (1) default to a generated JSON content index bundled into the Worker (`content-index.json`, queried in-memory, zero extra Cloudflare resources); (2) escalate to D1 (SQLite) only if a site's content volume or query needs outgrow comfortable in-memory handling; (3) escalate to Vectorize only if semantic search becomes a real requirement (most plausible for the docs site type). This mirrors the "simplest topology that can grow" philosophy already applied to the in-Worker architecture decision. Tool surface sketched per site type — *personal profile/CV:* `get_profile`, `list_experience`, `list_skills`, `list_projects`, possibly `get_resume`; *technical project log:* `list_entries`, `get_entry`, `search_entries`; *project documentation:* `get_toc`/`list_pages`, `get_page`, `search_docs`; *shared across all three:* `get_site_info` and a generic `search` — Owner
- **2026-06-07** — Confirm **`md4x`'s `renderToAnsi()` runs in the Cloudflare Workers runtime**, making in-Worker tier-ii Markdown → ANSI rendering for the terminal/CLI view (§7) viable with no separate build-time pipeline — Confirmed via source-level inspection of `md4x`'s WASM loader (`lib/wasm/default.mjs` and `lib/wasm/unwasm.mjs` in `md4x@0.0.25`), independent of the README's unverified "portable to Deno, Bun, edge workers" claim. Its automatic `init()` only auto-detects Node.js (via `process.getBuiltinModule("fs/promises")`) or bundler-specific `?url`/`?module` dynamic imports — neither path Wrangler supports — so calling bare `init()` would fail in-Worker. But `init()` also accepts a pre-instantiated `WebAssembly.Module` directly (the `input instanceof WebAssembly.Module` branch), which is exactly what Wrangler's native `.wasm` module imports produce. The viable integration is therefore: `import wasmModule from "md4x/build/md4x.wasm"; import { init, renderToAnsi } from "md4x/wasm"; await init({ wasm: wasmModule }); const ansi = renderToAnsi(markdown);` — a fully supported code path the library was designed to expose for exactly this portability case, not a workaround. Carries this one specific integration detail into the §7 implementation task — Owner
- **2026-06-07** — Confirm **Cloudflare's "Markdown for Agents" managed feature does reach Worker-served responses**, but **build `biblio`'s own hand-rolled negotiation+conversion path in §7 regardless**, treating the managed feature as an optional zone-level bonus rather than a dependency — Resolved via independent verification, which also corrected a wrong assumption baked into the original question (that availability hinges on "the Workers Pro plan"). What the research actually found: (1) **Reach is confirmed** — a real site running Workers + Static Assets (architecturally identical to `biblio`'s plan) gets full HTML→Markdown conversion through the managed `Accept: text/markdown` toggle, with `x-markdown-tokens`/`x-original-tokens` headers proving it operates on Worker-served output, not just classic proxied-origin HTTP; (2) **the actual gate is the zone's (domain's) plan tier — Pro/Business/Enterprise — not the Workers compute plan**, two separate Cloudflare billing constructs; the managed toggle is **unavailable on the Free zone plan** entirely, with no fallback; (3) **even where available, it has real constraints** — it requires an explicit `Content-Length` header (silently fails on chunked transfer encoding) and a response under roughly 1–2 MB (Cloudflare's stated origin-response cap is 2 MB; one independent tracker observed practical failures above ~1 MB) — `biblio`'s prerendered static-asset pages comfortably satisfy both, but this rules out leaning on it for any large dynamically-streamed Worker response; (4) **an independent author hit the same Free-plan gap and solved it exactly the way `biblio` already planned to** — generating purpose-built Markdown at build time and serving it via `Accept`-header content negotiation, specifically because doing so gives full control over output quality (no nav-chrome/footer/cookie-banner noise that a generic HTML→Markdown converter can't strip) and works on every plan tier including Free. Conclusion: §7's planned hand-rolled negotiation branch is the right baseline regardless of `biblio`'s zone plan — it's the only thing that works on Free, and it's strictly better-quality output than the generic converter even where Pro+ is available. The managed toggle remains worth flipping on later as a zero-cost zone-level supplement *if* a zone ever sits on Pro+, but `biblio` should not design around it or treat it as load-bearing — Owner
- **2026-06-07** — Scope `llms.txt` to a **minimal, build-time-generated file** — `site_name`/`description` plus a flat list of key page links derived directly from `content-index.json`, with no extra authoring step — rather than a fuller `llms-full.txt`-style content dump — Owner confirmed. Research already established that major LLM crawlers don't request `llms.txt` in meaningful volume yet — it reads as "expected convention to not be missing" rather than a proven traffic driver. A fuller dump would be real ongoing investment (size budgeting, staleness risk, format-spec churn as the convention itself is still settling) chasing a benefit that hasn't materialized. The minimal version satisfies "don't be conspicuously missing the convention" at near-zero cost — generated for free from the same content index everything else already derives from — and can expand later if usage data ever justifies it — Owner

Tiers i/ii (raw Markdown passthrough, plus the now-confirmed-viable in-Worker `md4x` → ANSI rendering) already cover the actual need: a terminal/CLI client gets a clean, readable view either way, with no separate build-time pipeline. A full tier-iii view would be a substantial speculative investment — a whole second styled view with its own design and testing surface — for a need that has not been validated, exactly the kind of "designing for hypothetical future requirements" the project explicitly avoids elsewhere (e.g., the no-MDX, no-charting-library, no-nested-`mcp`-config decisions above). It becomes a real, answerable question only if real terminal-client usage data ever shows demand for more than a clean ANSI render — at which point it gets its own research pass — Owner
