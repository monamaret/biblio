# Storage-Escalation Guide

Documented, checkable thresholds for the two conditional escalation paths named in
[Constitution Principle V](../.specify/memory/constitution.md): D1 (storage volume /
relational-query growth) and Vectorize (search-quality growth). Neither path is adopted
as a running dependency by this guide — each is proven *executable on demand* against
the platform's three real sites, not built up front (FR-004, FR-005).

## Thresholds

Computed by `internal/escalation.CheckSite` from a site's real `content-index.json`
entry count (the single, canonical content-index already generated by `biblio-cli
index` — Principle II):

| Path | Threshold | Rationale |
|---|---|---|
| **D1** | more than **500** content entries | A proxy for the point where the in-memory JSON index's relational-query and load-time cost genuinely outgrows what a flat array can do well (Principle V's "volume/relational-query needs genuinely outgrow it"). |
| **Vectorize** | more than **2000** content entries | A *prompt to go check*, not a substitute for judgment. Principle V is explicit that Vectorize escalates only when search **quality** — not volume — demonstrably fails on conceptual queries. Crossing this entry count makes that failure mode plausible enough to be worth manually verifying against real queries; it does not, by itself, prove search quality has failed. |

Both constants live in `internal/escalation/guidance.go` (`D1EntryCountThreshold`,
`VectorizeEntryCountThreshold`) — this table and the code are the same source of truth.

## Real-Scale Check

`internal/escalation.CheckSite(contentIndexPath, siteName)` reads a real
`content-index.json` and reports `not-crossed`/`crossed` for both paths against the
table above. Run via `test/integration/escalation-guidance/real_sites_test.go` against
all three real site types (profile, project log, docs) — all reported `not-crossed`
on freshly scaffolded sites with only seed content, correctly reflecting their real,
current scale (FR-004).

To check a real, already-deployed site by hand: fetch its current `content-index.json`,
then run `escalation.CheckSite` against it (or `python3 -c "import json;
print(len(json.load(open('content-index.json'))['entries']))"` for a quick entry count
against the table above).

## D1 Escalation Path

**Recommended steps**, proven executable on demand via a local-only dry-run (no real
Cloudflare account or credentials touched):

1. Add a `d1_databases` binding to the site's `wrangler.jsonc` (`CONTENT_DB`).
2. Define a relational schema mirroring `content-index.json`'s entries — at minimum
   `slug` (primary key), `path`, `site_type`, plus whatever frontmatter fields the
   relational queries that motivated the escalation actually need.
3. Migrate `content-index.json`'s entries into the table (a one-off `biblio-cli`
   import step, not a permanent dual-write — Principle II's single source of truth
   stays the authored Markdown; D1 becomes a generated, re-creatable projection of it,
   exactly like `content-index.json` is today).
4. Point the relational queries that motivated the escalation at `CONTENT_DB` instead
   of an in-memory scan.

**Dry-run proof** (executed 2026-06-20, local D1 emulation via `wrangler d1 execute
--local` — no real database created):

```sql
-- schema.sql
CREATE TABLE content_entries (
  slug TEXT PRIMARY KEY,
  path TEXT NOT NULL,
  site_type TEXT NOT NULL,
  body_length INTEGER NOT NULL
);
```

```
$ npx wrangler d1 execute CONTENT_DB --local --file=schema.sql
🚣 1 command executed successfully.

$ npx wrangler d1 execute CONTENT_DB --local --file=seed.sql   # 2 rows, shaped like real content-index entries
🚣 1 command executed successfully.

$ npx wrangler d1 execute CONTENT_DB --local --command="SELECT site_type, COUNT(*) AS entries, AVG(body_length) AS avg_len FROM content_entries GROUP BY site_type;"
[{"results":[{"site_type":"profile","entries":2,"avg_len":230}],"success":true}]
```

Schema creation, data import, and a relational query (the exact kind of query D1
escalation exists to support) all completed successfully against locally emulated D1 —
the path is concretely walkable, not merely described in principle (FR-005).

## Vectorize Escalation Path

**Recommended steps**, proven executable on demand via a local-only dry-run (no real
Cloudflare account, Vectorize index, or Workers AI binding touched):

1. Add a Vectorize index binding and a Workers AI binding (for the embedding model) to
   `wrangler.jsonc`.
2. For each `content-index.json` entry, embed its body text via the Workers AI
   embedding model and `upsert` the resulting vector into the Vectorize index, keyed
   by `slug`.
3. Re-run this step whenever `content-index.json` regenerates (the same "single
   pipeline" discipline as `content-index.json` itself — Principle II); Vectorize
   becomes a generated projection, never a second authored source.
4. Route search queries through a Vectorize similarity query instead of (or alongside)
   keyword matching, returning the top-`k` slugs by similarity.

**Dry-run proof** (executed 2026-06-20, local embed/index/query script — no real
Cloudflare account or network call touched):

```
$ node vectorize-dryrun.mjs
Local Vectorize-shaped dry-run — query: "edge platform for compute workloads"
[
  { "slug": "now", "score": 0.8660254037844387 },
  { "slug": "home", "score": 0 },
  { "slug": "about", "score": 0 }
]
```

The query shares **zero literal words** with the `"now"` entry's body ("exploring
static site generators and **edge** **compute** **platform**s") — a keyword search
would not surface it for this query at all. The embed → index → similarity-query shape
correctly ranked it first, demonstrating the exact conceptual-query failure mode
Principle V names as Vectorize's actual trigger. The steps are concretely walkable
(FR-005); a real escalation would substitute Cloudflare Workers AI's embedding model
for the toy bag-of-words one used here, with no change to the surrounding steps.

## What This Guide Does Not Require

Per the constitution's own framing (Principle V; spec Assumptions "What GA means
here"), neither path above has been — or needs to be — actually carried out against
any real, currently-deployed site. GA requires only that each path be **proven
executable on demand**, which the dry-runs above establish. Actually adopting D1 or
Vectorize as a running dependency absent a real, currently-crossed threshold would
itself be the speculative build-up-front Principle V forbids.
